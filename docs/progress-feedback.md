## 1. 问题与只读证据

此前一条真实任务在开始生成后约 85.4 秒才出现一次结构化重试提示，之后约 48.9 秒才出现文件变更。用户只能看到“生成中”，难以区分模型等待、工具执行、服务断连和任务卡住。

调查中 Runtime 账本保存 19 条源事件，API 也保存连续 1–19 的全部源事件，并逐条投影为公共活动；没有发现该样例被 API 丢弃事件。原始执行只有三个短阶段/重试消息，没有 message.delta。问题主要是执行层报告过少和 UI 缺少时间线/等待解释，并非轮询频率不足。

另有意图边界问题：当前输入框仍将输入创建为 build/plan Run，没有只读问答路由。询问使用方法可能被转成实现任务。本轮聚焦过程反馈，不把该缺口描述为已经解决。

## 2. 三层改进

| 层次 | 本轮内容 | 边界 |
| --- | --- | --- |
| Agent | 报告受控模板/源码快照准备、Planner/Worker 会话启动与就绪、计划摘要、结构化重试、接收文件与实际变更、类型/构建/浏览器检查开始和结果、候选打包与待发布 | 只报告真实调用与工具事实；不透传原始模型 JSON、凭证或隐藏思维，不虚构百分比 |
| 后端 | 逐条持久化已有消息/文件/检查事件，保留源发生时间；每个故障周期一次连接异常消息，成功同步后一次恢复消息，跨 API 重启去重 | 不通过连接消息伪造任务终态或释放项目锁；不改变已有 wire Schema |
| 前端 | 界面提供阶段、耗时、必要检查结果、文件变化、执行时间线、最后执行活动和独立 API 同步状态；刷新从历史事件恢复展示 | 单测/构建及本轮浏览器验收通过；历史仅恢复展示，不能用旧 run.updated 覆盖最新快照 |

Agent 仍采用每个 Run 的 Planner + Worker。项目级长期存活 Router、通用工具型 Worker、全局精确队列位置和完整意图路由均未在本轮实现，不能以“完整 Super-agent”介绍。

## 3. 执行活动与 API 同步的区别

- **执行活动时间**：来自 Agent 源事件，如模型会话就绪、文件实际变更或检查返回结果。后端的 activity.recorded 和源消息事件保留 source.occurredAt。
- **API 同步时间**：浏览器成功读取 API 的时间，只表示拿到了服务端状态；不能据此声称模型刚完成工作。
- **Run.updatedAt**：后端状态投影时间，不是模型心跳，也不是新执行结果的证明。
- **连接异常提示**：表明暂时无法同步执行服务进度，任务是否停止尚未确认；保留业务状态、锁和旧预览。
- **连接恢复提示**：在执行进度再次同步成功后记录，使用当前 API 时间；仅表示连接/同步恢复，不表示重放的旧活动刚发生。

项目 seq 是唯一排序/去重游标。断连补发的活动时间可能早于已收到的连接提示，仍按 seq 接收，不按时间重排。空轮询不产生新进度；回放旧事件不能重置“最后执行活动”为当前时间。已有数据库中的历史事件不会被回写或伪造为新增进展。

## 4. 可见内容与安全限制

本轮沿用现有 message.completed → message.updated 和 activity.recorded；不同进度消息 ID 会作为独立消息保存，同一消息的完整内容仍按协议 upsert。

断连/恢复消息使用固定脱敏文案，不包含底层异常原文、内部 URL、服务令牌或模型 Key。故障去重状态仅保存于后端 RunRecord，不加入公开 Run DTO；旧数据库记录缺少该可选字段时按未断连处理。

检查开始采用真实工具开始时发出的普通进度消息，检查结果仍以 check.completed 和真实证据为准。“必要检查完成 2/3”只统计已返回结果，不表示需求行为已验收；behavior=not_run 保持原义。

长时间没有模型结果时可以显示等待时长和停止入口。计时和同步正常都不能替代真实结果，也不能当作模型内部思考内容或准确剩余时间。
