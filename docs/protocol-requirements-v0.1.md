# Requirements authority 0.1.0 — frozen G0

This second G0 is separate from budget recovery. G0 Schema/fixtures/tests were frozen at241ce25 (supervisor shared check and122tests passed). API consumers are delivered separately; this document preserves the protocol and clarifies source/queue policy without changing DTOs. The API owns versioned requirement authority; Agent interprets messages and proposes a complete reviewable scope; Web presents that scope and asks the user to accept it. Existing execution/conversation/delivery DTOs and old message/proposal/report rows are not extended or rewritten.

## Minimal new objects

- `RequirementSource`: source message ID and exact user quote, optional genuine proposal/decision ID. Never fabricated natural-language authorization.
- `RequirementEntry`: stable API-allocated ID, original user text, kind goal/increment/constraint, source refs, authorization requested/suggested/confirmed, state active/withdrawn/superseded. `requested` means genuine requested scope, **not** permission to execute an old unaccepted proposal.
- `ProjectRequirementSnapshot`: ID/hash/revision/project, full entries and immutable source history, `base` either empty_project (no published app/source) or published_version (exact version ID and source hash when known), updatedAt. Every new snapshot has a new revision; older snapshots remain readable.
- `RequirementSummary`: own ID/hash/revision, existing strict `ChangeProposal`, exact snapshot ref and copied review scope, included entry IDs, explicit exclusion/replacement records with source evidence, acceptance→entry mapping, implementation kind new_app/modify_app. The proposal goal is the full cumulative target, not the last sentence. Empty-project basis permits only new_app; wording and model inputs must explicitly say no existing app exists.
- Typed acceptance request binds proposal revision, snapshot revision/hash and exact base. The user sees the entire target, requested inclusions, unaccepted suggestions, and any removal/replacement before accepting. Acceptance atomically records that complete scope and creates one Run under existing quotas/queue. No old unaccepted proposal becomes executable without this review.

## Suggested independent paths/wrappers

`@atoms/contracts/requirements`, version/header0.1.0 / `X-Atoms-Requirements-Version`; public GET `/api/requirements/v1/projects/:id` and GET `/api/requirements/v1/proposals/:id`; POST `/api/requirements/v1/proposals/:id/accept` is the unified explicit acceptance. Stale snapshot/base returns409, never automatically accepts changed scope. Old proposal accept routes must reject a requirements-bound summary unless the new exact review/accept path is used; old strict DTOs do not gain a requirements field.

Internal `/internal/requirements/v1/coordination-turns/:id` wraps the existing delivery-aware coordination request plus the authoritative requirement snapshot and an API-allocated current-message candidate entry ID/source text. The frozen request is persisted before its first PUT. The new response wraps the ordinary coordination snapshot plus typed proposed requirement deltas and full-summary mappings. Old context/facts hashes remain unchanged inside the outer wrapper. GET/events/cancel use the same independent wrapper strategy. Agent cannot directly write authority or grant execution.

API persists a current-message entry only after a structured clear-change result; consultation/status does not become a requirement merely because it appeared in chat. Prior active requested/confirmed entries must be included in the complete summary unless an explicit withdrawal/replacement is proposed with a source quote and shown to the user. Unaccepted model suggestions remain labelled suggestions; no inference grants them authority. The host validates ID/reference coverage and exact raw-source preservation; those structural checks are not a proof that model prose is semantically complete. Agent plan-quality review and user review remain necessary.

For the failed 3D example: the original game, 3D addition and computer-control request remain candidate sources. A new summary must say “build the first complete 3D game with computer control”, show all core/3D/control criteria and empty-project basis, then receive a new explicit accept. It must not pretend an existing game/source exists, rewrite the previous delta-only Seed, or charge a budget continuation against a known defective old plan.

## Frozen candidate route/purpose closure

The new typed `POST /api/requirements/v1/projects/:id/review` accepts `ReviewRequirementsRequest` (user-authored text plus exact expected snapshot) and returns the existing strict user-message/turn response. API records the actual submitted text as a real user message and fixes ask/plan, creating only a coordination turn. Web first fills an editable composer draft and labels it “整理完整需求（需发送）”; only the user's explicit send invokes this endpoint. It never submits automatically or fabricates authorization. The internal `purpose` is set by API to `scope_review` with the exact input message/snapshot; the Agent echoes `purposeUsed`. Such a review permits `newEntry=null` and cannot add/remove product requirements.

Ordinary existing message requests are always `interpret_message`: if the structured terminal outcome is change_proposal, a complete interpretation and the exact API-allocated current candidate are mandatory. A requested candidate must be included in the full summary; inferred suggestions must remain suggested and be either explicitly included for review or visibly excluded as unaccepted suggestions. No model may reclassify an ordinary “add AI” input as a review turn to omit it. Consult/status/clarify/control outcomes require interpretation=null. The **outcome**, not mode name, controls requirement candidates: ask-mode explicit change_proposal can save requested candidates and a full review proposal but never confirm, remove/replace scope or create a Run automatically. This preserves the actual three-ask game→3D→AI planning flow.

For typed clarification answers, the candidate source retains the full trusted question text and question/clarification IDs in addition to the exact answer quote. Its host-composed requirement text is `question + "\n用户回答：" + answer`; the old complete operation snapshot remains authoritative even when the question is outside recent history. Arbitrary labels or unbound short answers must not become authorization. The host validates every source ID/quote against owned stored data, not just schema syntax.

Historical pending summaries may be returned for reading with their original embedded snapshot/revision/base. They are not silently retargeted to the newest snapshot. Accept requires current exact snapshot/base and proposal/summary revision; any difference returns409, including an old v2 accept attempt on a summary requiring full review. Repeated/cross-session typed acceptance must refer to the same already-authorized Run, never a second quota charge. The API separately records real acceptance provenance; Agent cannot set confirmed authorization. A later immutable authority snapshot may mark the reviewed included entries confirmed, without changing the old messages, proposals, source snapshots or failed Seed/report.

Source basis is explicit: empty_project has no published source and can only propose new_app; published_version requires exact version ID and an actual source hash when sourceAvailable=true, otherwise hash=null and modification is not admissible. This source hash identifies available bytes, not a claim that legacy code passed verification. Review mapping/coverage checks preserve structure and the user's authority; they do not prove arbitrary natural-language semantics.

The independent modules use `X-Atoms-Requirements-Version:0.1.0` on every new route/wrapper, echoed on successful HTTP responses. PUT accepts identical frozen request/hash, refuses differing body for the same turn; new wrapper GET/events/cancel preserve request purpose/snapshot refs and use existing coordination cancellation semantics. No old DTO accepts a new requirements field. Producers/consumers independently calculate canonical hashes excluding only each object's own top-level hash and validate actual source provenance.

## Consumer policy clarification (no DTO expansion)

A first complete explicit intent that is already authorized/building is distinct from multiple unaccepted planning requests. A later clear auto/latest intent may queue behind that first build; dispatch uses its actual latest successful source plus the complete authorized cumulative Seed, not a forced template merely because the earlier Router snapshot was empty. Typed scope_review/refresh proposals instead lock exact_version (including null) and reject head drift before Prepare. Ordinary proposals retain their declared latest/exact policy, and UI must distinguish the two from the precise state check at acceptance.

External typedaccept and budgetcontinue additionally refuse while a later ordinary text/short-answer turn is queued/running/cancelling or a clarification remains open. Typed status/sharing operations are known read-only exceptions. Auto materialization excludes its own active turn from this check; it does not block itself or silently ignore a later unparsed intent. After a genuine scope change commits, the old summary/quote is stale. No pending question is auto-answered or transformed into an accepted requirement.
